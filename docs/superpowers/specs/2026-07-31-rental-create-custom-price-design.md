# Своя цена позиции при создании аренды

**Дата:** 2026-07-31
**Статус:** одобрено, в реализации

## Цель
В форме создания аренды администратор может задать цену за сутки для конкретной
позиции — **до** создания аренды, прямо при выборе товара. Цена относится только
к этой аренде и не влияет на справочник товара.

## Контекст
`RentalItem.price_per_day` уже является снимком, независимым от
`Product.daily_price` (`config/models.py`). Изменить его сегодня можно только
**после** создания аренды — через модалку правки позиции
(`RentalItemEditView`, только админ). При создании цена жёстко берётся из
справочника: `price_per_day=product.daily_price` в
`RentalCreateView._create_rental`.

Модель и миграции менять не нужно — меняется только путь ввода данных.

## Решения (согласовано с заказчиком)
- **Права:** менять цену может **только админ** (`user_is_admin`). Согласуется с
  `RentalItemEditView`, где правка цены уже под `AdminRequiredMixin`.
- **Охват:** только форма создания аренды — полная страница «Новая аренда» и
  модалка создания с карточки клиента (обе рендерят общий `_rental_form.html`).
  Модалка «Добавить позицию» к существующей аренде (`RentalItemAddView`) в
  этот объём **не входит**.
- **Валидация:** любая цена ≥ 0. Ноль допустим (бесплатная выдача).

## Подход
В строке позиции формы появляется поле «Цена/сут.» (`name="item_price"`),
видимое только админу. Значение автоматически подставляется из справочника при
выборе товара, но админ может его переписать. Сервер принимает это поле только
от админа.

## Компоненты

### `_item_row.html` — колонка цены
Новая раскладка строки: товар `col-md-4`, кол-во `col-md-2`, цена `col-md-2`,
подытог `col-md-3`, кнопка удаления `col-md-1`.

Поле рендерится под `{% if is_admin %}` (`is_admin` приходит из контекст-
процессора `navigation`, доступен и в htmx-фрагменте новой строки
`rental_item_row_new`, потому что тот тоже рендерится через `render(request, …)`).

```
<input type="text" name="item_price" inputmode="decimal" autocomplete="off"
       class="form-control money-input item-price" value="{{ row.price }}">
```

Используется проектная конвенция денежного поля (`money-input`): та же, что у
`initial_deposit` в этой же форме. `static/js/money-input.js` сам цепляется к
таким полям, в том числе к строкам, добавленным через htmx, показывает
`40 000` и снимает пробелы перед отправкой. `type="text"`, а не `number` —
иначе браузер не даст ввести пробелы-разделители.

Справочная цена товара остаётся видна в самом пикере
(`_item_product_picked.html` показывает `· {{ product.daily_price }}/сут.`), так
что отклонение от прайса заметно без дополнительных бейджей.

### `static/js/rental-create.js` — автоподстановка и расчёт
- При выборе товара (событие `htmx:afterSettle`) поле цены строки заполняется
  значением из `data-price` скрытого `input[name="item_product"]`.
- Подстановка происходит только если у скрытого `item_product` **непустое**
  значение. При сбросе товара («сменить») пикер возвращается в состояние поиска
  с `value="" data-price="0"` — обнулять из-за этого цену не нужно.
- Если админ правил поле руками, оно помечается `data-touched="1"` и больше не
  перезаписывается при смене товара. Это та же идиома, что уже применена для
  автозаполнения `due_date` в этом же файле.
- После программной установки значения поле получает событие `input`, чтобы
  `money-input.js` отформатировал его (`40 000`), а расчёт формы пересчитался.
- `recalc()` берёт цену из `input.item-price`, если он есть и заполнен; иначе —
  из `data-price` (поведение для staff и старый fallback на `select`). Перед
  разбором снимает пробелы и меняет запятую на точку — в поле лежит
  отформатированное значение.

### `config/views.py` — разбор, валидация, создание
- Хелпер `parse_money(raw)` — в `config/forms.py`, рядом с уже существующим
  `_strip_money_spaces`, поверх которого он и строится (тот аккуратно снимает
  пробелы-разделители только при корректной группировке и нормализует запятую
  в точку). Возвращает `Decimal`, округлённый до копеек, либо `None`, если
  значение не разбирается в число. `RentalItemEditView.post` переводится с
  собственной инлайновой нормализации на этот хелпер, чтобы логика разбора
  денег не жила в трёх местах.
- `RentalCreateView._parse_item_rows` дополнительно читает
  `post.getlist('item_price')`. Списки `item_product` и `item_qty` уже выровнены
  по строкам (скрытый `item_product` рендерится даже пустым — см. комментарий в
  `_item_product_search.html`). Цена читается **по индексу строки**, а не через
  `zip`: у staff поля нет вовсе, список пустой, и `zip` бы обнулил все строки.
  Отсутствующий индекс трактуется как «цена не задана».
- Цена принимается только если `user_is_admin(request.user)`. Иначе поле
  игнорируется целиком — staff не может задать цену подделкой POST. Метод
  `_parse_item_rows(post)` получает дополнительный аргумент — флаг «это админ»;
  вызов в `post()` передаёт `user_is_admin(request.user)`.
- Заготовки строк, которые создаёт сервер (`_initial_context` и
  `ItemRowNewView`), получают ключ `'price': ''`, чтобы шаблон рендерил пустое
  поле, а не строку `None`.
- Пустая строка → цена не задана, берётся `product.daily_price` (не ошибка).
- Непарсимая или отрицательная → ошибка в общем блоке `item_errors`, аренда не
  создаётся.
- `_create_rental` использует цену строки, если она задана, иначе
  `product.daily_price`.
- `_rows_for_template` возвращает введённую цену обратно в форму, чтобы при
  ошибке валидации ввод админа не терялся (так уже сделано для `qty`).

## Тексты ошибок
- Непарсимая цена: `Строка %(i)d: цена за сутки указана неверно.`
- Отрицательная: `Строка %(i)d: цена за сутки не может быть отрицательной.`

Формат совпадает с уже существующими ошибками позиций в `_validate_items`
(`Строка %(i)d: …`). Обёрнуты в `_()`, как остальные строки модуля.

## Крайние случаи
- **Staff.** Поля в HTML нет; `item_price` в POST игнорируется; цена берётся из
  справочника — поведение не меняется.
- **Пустая цена у админа.** Не ошибка: подставляется цена справочника.
- **Цена 0.** Допустима — бесплатная выдача.
- **Формат `1 234,50`.** Разбирается в `1234.50` (пробелы, неразрывные пробелы,
  запятая как разделитель дробной части).
- **Несколько позиций.** Цены не перепутываются между строками — выравнивание
  по индексу строки.
- **Ошибка валидации.** Форма перерисовывается, введённые цены сохраняются.
- **Справочник.** `Product.daily_price` не изменяется ни при каких вводах.

## Что не меняется
Модель `RentalItem` и миграции, биллинг (`config/billing.py`), контракт и
чек возврата (PDF/печать), модалка «Добавить позицию» к существующей аренде,
модалка правки позиции (кроме перевода на общий хелпер парсинга цены).

## Тесты
Новый файл `tests/test_rental_create_price.py`:
1. Админ передаёт `item_price=250.50` → `RentalItem.price_per_day == 250.50`,
   `Product.daily_price` не изменился.
2. Пустая цена → подставляется `product.daily_price`.
3. Формат `1 234,50` → `1234.50`.
4. `abc` → ошибка в ответе, аренда не создана.
5. Отрицательная цена → ошибка, аренда не создана.
6. Цена `0` → аренда создана, `price_per_day == 0`.
7. Staff шлёт `item_price` → игнорируется, применяется `daily_price`.
8. GET формы: поле `item_price` есть в HTML у админа и отсутствует у staff.
9. Две позиции с разными ценами → цены не перепутаны.
10. При ошибке валидации введённая цена возвращается в перерисованную форму.

Существующий набор (`pytest`) остаётся зелёным — в частности
`tests/test_rental_item_price_edit.py`, который покрывает хелпер парсинга через
`RentalItemEditView`.
